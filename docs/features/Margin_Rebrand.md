# Margin rebrand — J-Star Projects

## Goal and scope

Direction A, **Margin**, in `docs/mockups/rebrand-directions.html` is the visual source of truth. This document translates that concept into the active student-facing screens. The audience is final-year students starting a project, returning to a draft, or asking the J-Star team for help. Keep the existing DIY and agency journeys distinct. The customer-facing product name is **J-Star Projects**; J-Star remains the service owner. Replace visible “J-Star FYB”/“J Star.FYB” branding on the affected screens, not stored project data or route names. The mockup's sample topic, sources, saved indicator and prose are illustrative, not seeded content or claims about live data.

This is a client-side presentation change only. Keep current server actions, authentication, payments, project loading/saving, AI generation, research processing, API routes, data flow and database schema unchanged. No migration, new component library, canvas/WebGL, particles or scroll hijacking. The requirements document describes an animated agency landing page; for this approved direction, retain its functional countdown, pricing, gallery and consultation paths while replacing the sci-fi styling with a restrained notebook treatment. Do not remove working sections to match the shorter concept plate.

## Tokens and type

Use the same light palette across marketing and app; avoid purple/cyan glows and dark glass panels. Ratios below are WCAG contrast ratios for the stated solid pairings, rounded to two decimals; do not place text over translucent variants without checking the resulting color.

| Role | Color | Use and contrast |
| --- | --- | --- |
| Canvas / paper | `#EDF1ED` | Page background; ink on paper **10.33:1**. |
| Writing surface | `#FFFEFA` | Editor, form and content panels; ink on writing **11.68:1**. |
| Ink | `#193E35` | Headings, body, icons and secondary button text. |
| Muted ink | `#52685F` | Supporting copy only; **5.25:1** on paper, **5.94:1** on writing. |
| Rust / action | `#B34D39` | Primary buttons, links, active-step rule; `#FFFEFA` text on rust **5.15:1**. Rust text on paper **4.56:1**, on writing **5.15:1**. |
| Rule | `#C9D3CA` | Borders and dividers only; **1.52:1** against writing, so never use as text or the sole cue for a control/state. |
| Soft selection | `#E1E9E1` | Selected row and subtle emphasis; ink **9.51:1**, muted ink **4.84:1**. |

Use **DM Sans** (400/500/600/700/800) for interface and headings, falling back to Arial, then sans-serif. Use **IBM Plex Mono** (500/600), falling back to monospace, only for chapter numbers, short labels and metadata; keep labels legible rather than using tiny all-caps throughout. Desktop hero 56–72px / 1.03; mobile hero 36–44px / 1.1. Page headings 28–36px / 1.15, panel headings 20–28px / 1.2, body 16px / 1.5–1.65, controls 14–16px, metadata at least 12px. Avoid the mockup's 10px text in the real app. Keep long writing text in a readable 65–75-character measure.

## Layout and component rules

- Limit page content to about 1200px with 24–32px desktop gutters and 16–20px mobile gutters. Use a 4/8px spacing rhythm; section gaps 48–72px desktop, 32–48px mobile. Inside panels use 16–32px. Keep rules 1px; avoid stacked shadows and extra cards. Radius 4–6px for controls/panels. A single shallow offset shadow may mark the hero paper or writing surface, not every card.
- **Chapter margin signature:** a 4–5px rust rule on the *left edge of the current document or chapter preview*, beside an ink chapter heading and mono chapter ID. On chapter navigation, use a 3px rust rule on the selected item against the soft selection surface. Never use the rule for every row, every card or the whole application shell. Pair it with text such as “Current chapter” or an active heading; color alone does not indicate state. Do not draw the rule into editable document content or export.
- Primary action: rust fill, writing-surface text, 4–6px radius, 44px minimum touch height. Secondary action: transparent or writing surface, ink text, visible rule border. Links: rust text with underline on hover and focus, not color alone. Disabled actions: clearly labeled and visually distinct, never conveyed by opacity alone. Inputs: writing surface, ink text, visible border and persistent labels; error text in ink with explicit message and field association. Reserve rust for action/current location, not error or success. Status chips should state “Saving…”, “Saved”, “Not saved” or the actual current state in ink/muted ink; never show the concept's “Saved” as a permanent decoration.
- Loading keeps the same page hierarchy with short status text and a stable content area; empty screens explain the next available action; errors identify the failed action and offer the existing retry or recovery path. Do not imply a file is sourced, generated or saved before the live state confirms it.

## Responsive and access rules

At roughly 780px and below, stack hero and forms, keep actions full-width when needed, and collapse workspace side rails into the existing mobile navigation/views. At tablet width prioritize the editor over both rails; at narrow phone widths allow chapter labels to wrap or scroll horizontally without clipping controls. Do not place the context shelf beneath a long draft as the only way to reach research. Test 320px through wide desktop and 200% zoom without horizontal page overflow; allow local scrolling in navigation where needed. Keep interactive targets at least 44×44px and provide a visible 3px rust focus ring with 3px offset (or an equally clear ink ring against rust buttons). Keyboard order follows the visual reading order; tabs and dialogs retain labels, escape/close behavior and focus return. State must be stated in text or accessible labels, not only a colored dot or rule. Respect `prefers-reduced-motion`: no floating, pulsing, parallax or smooth-scroll dependency; limit optional hover movement to subtle color/border changes. Updates such as save and payment verification remain understandable without animation.

## Handoff and copy checks

Apply tokens and shared controls first, then landing/auth, dashboard/builder, then the active v2 editor and research rail. This is styling/copy guidance, not permission to change business behavior. Marketing claims must match the current offer: retain live pricing, eligibility, timer logic and functional CTAs rather than copying the concept's placeholder copy or fixed figures. “Ask Monji” and any research/saving claims should only appear where those named capabilities and states are actually available; verify the live assistant name on each surface before replacing existing labels. Keep agency assistance as an option, not a promise of automated completion. The unresolved design check is the real-content pass: review live long project titles, empty research, auth errors, locked projects and small screens before declaring the rebrand complete.
