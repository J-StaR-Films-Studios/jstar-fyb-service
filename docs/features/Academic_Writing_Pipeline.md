# Evidence-aware academic writing

## Goal and rollout

The builder can draft a five-chapter document from a saved project without requiring the user to co-write each section. The existing Research tab supplies discovered papers and uploaded materials; this phase does not claim that the writing run discovered or read sources that are absent from the project. It does not claim missing experiments, measurements, implementation steps or citations. A full run creates the missing chapters, keeps existing editor content, and records drafts that need review. An optional chapter or section run changes only the requested part. Existing generation remains available with the flag off.

Set `ACADEMIC_PIPELINE_ENABLED=true` on the server and `NEXT_PUBLIC_ACADEMIC_PIPELINE_ENABLED=true` in the client build. Optionally set `ACADEMIC_PIPELINE_PLAN_EFFORT`, `ACADEMIC_PIPELINE_DRAFT_EFFORT`, `ACADEMIC_PIPELINE_BASELINEDRAFT_EFFORT`, `ACADEMIC_PIPELINE_EDITORIALREVIEW_EFFORT`, `ACADEMIC_PIPELINE_EDITORIAL_EFFORT`, `ACADEMIC_PIPELINE_FACTUALREVIEW_EFFORT`, `ACADEMIC_PIPELINE_REVISION_EFFORT`, `ACADEMIC_PIPELINE_POSTREVISIONREVIEW_EFFORT` or `ACADEMIC_PIPELINE_ABSTRACT_EFFORT` to `low`, `medium` or `high`. These settings keep the existing provider/model router and are recorded with pipeline version `academic-v1` on each run. Apply the local Prisma migration `20260925112924_writing_pipeline` to a confirmed nonproduction database with the repository's migration process. Regenerate Prisma Client. Do not enable the flag before migrating. No detector integration or document upload to a detector is included.

## Components and data flow

- `Project`, `ChapterOutline`, `Chapter` and `ResearchDocument` remain the source materials. `ProjectFact` records a statement as planned, completed, user-reported, artifact-backed, unknown or conflicting. An artifact-backed fact must refer to an uploaded project document or data file. The app does not independently certify that the artifact supports the statement.
- `ResearchDocument` holds optional DOI, URL, passage, location, material level, verification note and limitations. A discovered abstract or web snippet stays at that level even if Gemini File Search indexed synthesized metadata. Uploads with extracted text have an `UPLOADED_TEXT` level. Missing title, author, year and page are never filled from a filename.
- `assemble` captures topic, outline, five chapter targets, facts and bounded source passages/summaries. It retains each complete source text's SHA-256 digest instead of copying the whole file into every run. Editing materials changes the digest for new snapshots. A comparison may deliberately reuse an earlier immutable snapshot using `snapshotRunId`.
- `WritingRun` stores the snapshot/hash, variant, pipeline/prompt version, stage efforts, stages, drafts, editorial review, revision history, factual concerns, validation findings, stage provider/model, token counts when returned, timings and failures. `Project` owns each run; detector measurements belong to a run. There is no price estimate without provider cost data.
- The shared service plans chapter arguments, drafts using source ID markers, reviews writing problems, revises affected chapters, reviews factual claims, repairs affected chapters once, rechecks changed passages, runs deterministic checks, assembles cited references and creates an abstract if the project lacks one. It validates an existing abstract rather than overwriting it. A model concern remains uncertain. It blocks verified export if the flagged excerpt survives revision or the post-revision check finds a new concern. Removing the excerpt and passing that check clears the specific finding, but a clean model review is not proof of factual support. Deterministic checks cover missing IDs/metadata, model-written reference lists, changed numbers, project-result percentages without a matching artifact-backed fact and passage, abstract/full-text overclaims and conflicting measurements. Only source IDs cited in the published chapters or abstract produce bibliography entries. Saved abstracts render source markers from stored metadata before export. A passage that fails checks is not published. Only a `full` run publishes automatically; comparison variants remain drafts until a chapter is explicitly applied. Reviewer concerns and missing results keep the run in `NEEDS_REVIEW`.
- `publishRun` writes missing or empty chapters and edits a scoped section only if its starting version and content hash still match. Existing full chapter content is left alone. After evidence changes, a new full run re-reviews earlier generated text if its saved hash still matches; it certifies identical content without replacing it. Changed passages need explicit chapter-by-chapter application through `/writing/runs/{runId}/apply`, with an editor-history snapshot and the same version/hash check. Applying a prior chapter of a full run refreshes Chapter 5 references if Chapter 5 still matches that run's published hash. Old drafts and revisions remain in the run. Concurrent edits cannot be silently replaced.
- The flagged `/api/generate/chapter` and `generateSection` tool use the same pipeline. The unflagged paths retain the current router and behaviour except for safety corrections to existing chapter overwrites, fabricated fallback text and filename references. The workspace comparison view starts a full run by default. It shows gaps, versions, diffs and blind A/B labels. Closing it reloads saved chapters unless there are unsaved edits.
- A flagged submission export requires a completed latest full run with no findings, matching saved chapter hashes/versions, a matching abstract and a bibliography matching the final cited sources. The server DOCX endpoint and workspace/wizard/PDF/Markdown controls consult the readiness check. Client Markdown/PDF exports fetch the saved abstract and chapters rather than cached editor text; a failed fetch blocks the export. A generated draft with unresolved gaps is not a verified submission document. Raw drafts and run records remain accessible to the project owner for review and comparison.

## Scoped API

All writing endpoints require an authenticated owner and return 404 when the flag is off. `GET/POST /api/projects/{id}/writing/facts` lists or records facts; `PATCH/DELETE /facts/{factId}` corrects them. `GET /writing/evidence` lists project source IDs and material levels; `PATCH /evidence/{sourceId}` updates supplied metadata and passages without raising an abstract to full-text status. `GET/POST /writing/runs` lists or starts a run. POST requires `idempotencyKey`, `variant` (`baseline`, `context`, `editorial`, `full`), and optionally `snapshotRunId`, `scope: {chapterNumber?, section?}` and `tonePreference`. Keep the same key when retrying a network request. A reused snapshot must have exactly the requested scope; leaving scope out means the complete document, not the source run's chapter scope. `GET/PATCH /runs/{runId}` inspects or resumes/cancels a failed or stale run. Cancellation takes effect between stages. `POST /runs/{runId}/apply` with `{chapterNumber}` explicitly applies one chapter draft from a finished run when the saved chapter still matches the run snapshot. `GET /writing/export-status` checks the saved document. `POST /runs/{runId}/measurements` requires detector name, optional version, measurement date, raw JSON result, tested version `final`, SHA-256 hash of the selected run's final texts joined with two newlines, and optional processing limitations. The server checks that hash.

The application runs within the existing request time limit (`maxDuration=300`). A provider failure leaves completed chapter stages available for explicit resume; a stale `RUNNING` lease can be resumed after ten minutes. This is not a background queue. Avoid large input sets until request-duration and crash recovery are tested under production load. Source processing is reused through stored snapshots; there is no additional vector index for this phase.

## Reproducible comparison

Use synthetic development fixtures for automated tests. Do not put experiment topics or user documents in the repository. For a real evaluation, choose a separate, consented set of projects with confirmed facts, artifacts and research metadata. Use the same project snapshot and chapter scope across four runs. Start `baseline` on current materials, then start `context`, `editorial` and `full` with `snapshotRunId` set to the baseline run ID and a new idempotency key per run. In the workspace view, select the baseline as A and check "Reuse A inputs" for each comparison run. Leave that checkbox off for ordinary automatic writing so a new run includes the latest project materials. Check equal `snapshotHash` in the workspace panel before interpreting differences. Baseline uses the current chapter prompt rules and configured router but runs through the new safe ID-based writer and persistence. It is a *legacy-prompt approximation*, not a replay of historical streaming output or old Gemini retrieval.

Blind human reviewers to variant names. Score readability, project specificity, coherence and factual quality separately on a 1–5 scale; the current ratings are local to the comparison view and included in its JSON export, not stored on the server. Inspect the split diff, model concerns, citations, source availability, stage timings, token counts and unresolved findings. Cost is shown only when a provider actually returns it. Keep human ratings and source checks distinct from optional detector measurements.

To import a detector result, run the vendor tool yourself on the exact selected final text, then paste its raw JSON result, vendor/version, date and processing limitations into the comparison view. This application does not send text to a detector. A vendor percentage is a vendor output, not a probability of AI authorship, and different vendor scores must not be averaged. Do not rewrite until a detector passes. Export the comparison JSON and retain the model/prompt version, snapshot hash and detector-tested hash with any review notes. The writing checks are not a comprehensive plagiarism scan.

## Local verification

Run `npx prisma validate`, `npx prisma generate`, `npx tsc --noEmit --incremental false`, and `npx --no-install tsx --test src/lib/writing/*.test.ts`. The synthetic fixtures exercise an abstract-only claim, a changed number, conflicting chapter numbers, missing results, provider interruption and resume, edit preservation, re-review after evidence arrives, project access and a complete mocked draft-to-export-readiness flow. They do not call a live model, migrate a database or render a real DOCX. Run those checks with a disposable, confirmed test database and a configured provider before enabling the flag for users.

## Current boundaries

The model cannot verify that a citation truly supports a sentence beyond the available passage. Metadata, abstracts and cropped extracted text limit that judgment; the UI must leave it uncertain. Bibliography formatting is metadata-derived but not a complete APA formatter. A chapter-specific run cannot certify the whole document for submission. Claim-specific checks for project percentages still cannot independently establish that an uploaded artifact supports every interpretation; the model review can flag concerns but is not proof of correctness. Explicitly applied edits need a later full run to restore export readiness. No database migration, live provider call or real DOCX render was used for the synthetic flow tests. Local `prisma generate` and TypeScript checks pass. Database-backed integration still needs a confirmed disposable test database.
